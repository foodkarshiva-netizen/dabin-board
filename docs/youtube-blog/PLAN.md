# 유튜브 요약 블로그 자동화 — 설계 초안 (v0.1)

> 목표: 유튜브 채널을 고르면, 새 영상이 올라올 때마다 **상세 요약 + 이해를 돕는 이미지**가 포함된 글이 블로그에 자동으로 게시되는 파이프라인.
> 상태: 초안. 아래 "결정이 필요한 항목"이 확정되면 Phase 0부터 착수.

---

## 0. 한눈에 보기

```mermaid
flowchart LR
  A[채널 등록<br/>channel_id] --> B[새 영상 감지<br/>RSS / WebSub / Data API]
  B --> C[수집<br/>메타데이터·자막·챕터<br/>(자막 없으면 STT)]
  C --> D[요약 파이프라인<br/>구간 분할 → 구간별 상세 → 종합]
  D --> E[비주얼 생성<br/>인포그래픽·다이어그램·<br/>(선택) 장면 캡처]
  E --> F[글 조립<br/>Markdown/HTML + SEO 메타]
  F --> G{승인 게이트<br/>다빈보드 푸시}
  G -->|승인/자동| H[블로그 발행<br/>WordPress / 정적사이트]
  G -->|반려| D
  H --> I[모니터링<br/>비용·실패·조회수]
```

핵심 설계 원칙 4가지

1. **상태 머신 기반**: 영상 하나가 `discovered → fetched → summarized → illustrated → drafted → approved → published` 를 거치며, 각 단계는 재실행 가능(idempotent). 중간에 죽어도 그 단계부터 다시.
2. **요약은 "근거 있는 상세함"**: 모든 문장이 타임스탬프에 묶이도록 구조화 출력(JSON)으로 뽑고, 그 다음에 글로 렌더링. LLM이 자유롭게 산문을 쓰게 두면 길이는 늘지만 정확도가 떨어짐.
3. **이미지는 "생성 우선, 캡처는 보조"**: 남의 영상 장면 캡처는 저작권·애드센스 리스크가 있으므로, 내용을 재구성한 인포그래픽/다이어그램을 기본으로 하고 캡처는 채널별 옵션.
4. **처음엔 사람이 승인, 신뢰가 쌓이면 자동**: 승인 게이트를 다빈보드(이미 Firestore + FCM 푸시가 있음)에 붙여 휴대폰에서 검토 → 발행.

## 1. 요구사항 분석

| # | 요구사항 | 해석 | 난이도 | 핵심 리스크 |
|---|---|---|---|---|
| [1] | 채널 고르면 자동 게시 | 채널 감시 + 스케줄러 + 무인 발행 | 중 | 블로그 플랫폼이 API를 제공하는가 |
| [2] | 요약이 상세하고 정확 | 자막 확보 + 다단계 요약 + 검증 | 중상 | 자막 없는 영상, 환각(없는 말 지어냄) |
| [3] | 내용에 맞는 캡처/이미지 | 타임스탬프 기반 캡처 + 생성 이미지 | 상 | 저작권, "말하는 얼굴"만 찍히는 무의미한 캡처 |

숨은 요구사항(운영 관점)

- **검색 노출/수익화**: 단순 요약 블로그는 구글의 "대량 생성 콘텐츠" 정책과 애드센스 심사에서 불리. 원 영상에 없는 부가가치(배경 설명, 관련 자료, 비교, 용어집)를 파이프라인이 자동으로 얹어야 함.
- **비용 상한**: 영상당 비용을 알고, 월 예산을 넘으면 멈춰야 함.
- **실패 가시성**: 자막 실패·발행 실패가 조용히 묻히면 블로그가 멈춘 줄 모름 → 푸시 알림.

## 2. 단계별 상세 설계

### 2.1 채널 감시 (Discovery)

세 가지 방법을 비교하면:

| 방법 | 비용/할당량 | 지연 | 비고 |
|---|---|---|---|
| RSS `youtube.com/feeds/videos.xml?channel_id=…` | 무료, 무제한 | 폴링 주기(10~30분) | 최근 15개만. **기본 채택** |
| WebSub(PubSubHubbub) 푸시 | 무료 | 거의 실시간 | 공개 HTTPS 엔드포인트 필요, 구독 갱신(10일) 필요 |
| YouTube Data API v3 `playlistItems.list` | 일 10,000 유닛(호출당 1) | 폴링 | 메타데이터·챕터·썸네일 URL은 어차피 여기서 가져옴 |

권장: **RSS로 감지 → Data API로 상세 메타데이터**. 폴링은 30분 간격 스케줄러(GitHub Actions cron / Cloud Scheduler + Cloud Run Job). 라이브/프리미어/쇼츠는 채널 설정으로 제외 가능하게.

채널 설정 예시(Firestore `yt_channels/{channel_id}`):

```json
{
  "channel_id": "UCxxxx",
  "title": "채널명",
  "enabled": true,
  "min_duration_sec": 180,
  "skip_shorts": true,
  "language_hint": "ko",
  "visual_policy": "generated_only",   // generated_only | generated_plus_capture
  "publish_mode": "review",            // review | auto
  "blog_category": "IT/AI",
  "prompt_overrides": { "tone": "…" }
}
```

### 2.2 수집 (Ingest)

자막 확보 우선순위:

1. **업로더 자막**(수동) → 가장 정확
2. **자동 생성 자막**(ASR) → 고유명사 오타 많음, 요약 프롬프트에 "자막은 자동생성이라 오탈자가 있을 수 있음"을 명시
3. **자막 없음** → 오디오 추출 후 STT(Whisper 계열). 20분 영상 기준 수 분 소요, 비용 발생

주의: 자막 API(youtube-transcript-api)는 클라우드 IP에서 차단되는 경우가 잦음 → 프록시 또는 yt-dlp 자막 다운로드로 폴백. 공식 Data API의 `captions.download`는 **본인 채널 영상만** 가능하므로 타인 채널 자동화에는 못 씀. 이 부분은 YouTube 약관상 회색지대라는 점을 인지하고 운영해야 함.

함께 수집: 제목, 설명(설명란의 챕터 타임스탬프 파싱), 태그, 썸네일 URL, 길이, 게시일, 조회수.

### 2.3 요약 파이프라인 (핵심)

"상세하게 잘" 되려면 한 번에 요약하지 말고 **4패스**로 간다.

```
Pass 0  전처리      자막 정리(중복 제거, 문장 단위 병합, [mm:ss] 유지)
Pass 1  구간 분할    설명란 챕터가 있으면 그것을 쓰고, 없으면 LLM이 주제 전환점 기준으로 5~12개 구간 생성
Pass 2  구간별 상세  각 구간: 핵심 주장, 근거/사례, 수치, 인용문(타임스탬프), 용어
Pass 3  종합        전체 한줄 요약, 3~5개 핵심 포인트, 구간 요약 연결, 결론/시사점, FAQ, 용어집
Pass 4  검증        "요약의 각 주장이 자막에 실제로 존재하는가" 체크 → 근거 없는 문장은 삭제/수정
```

구조화 출력 스키마(요약 결과, 발췌):

```json
{
  "one_liner": "…",
  "key_takeaways": [{"text": "…", "ts": "12:40"}],
  "sections": [{
    "title": "…", "start": "00:00", "end": "05:12",
    "summary": "3~6문장",
    "details": ["…", "…"],
    "quotes": [{"text": "원문 인용", "ts": "03:10"}],
    "numbers": [{"label": "…", "value": "…", "ts": "04:02"}],
    "visual_suggestion": {"type": "diagram|chart|card|capture", "spec": "…"}
  }],
  "glossary": [{"term": "…", "definition": "…"}],
  "faq": [{"q": "…", "a": "…"}],
  "added_value": {"background": "…", "related_links_query": ["…"]},
  "seo": {"title": "…", "slug": "…", "description": "…", "tags": ["…"]}
}
```

모델·비용 전략

| 단계 | 모델 | 이유 |
|---|---|---|
| Pass 1 구간 분할, Pass 4 검증 | `claude-haiku-4-5` 또는 `claude-sonnet-5` | 기계적·판별 작업, 저렴 |
| Pass 2·3 상세 요약/종합 | `claude-opus-5` | 글 품질이 곧 블로그 품질 |
| 이미지 캡션/프레임 판별(비전) | `claude-sonnet-5` | 저렴하고 충분 |

- 자막 전체를 시스템/첫 메시지에 넣고 **프롬프트 캐싱** → Pass 2를 구간 수만큼 돌려도 입력 비용은 한 번만.
- 실시간일 필요가 없으므로 **Batch API(50% 할인)**로 처리. 30분 폴링 + 배치 지연이면 게시까지 1~2시간, 요약 블로그로는 충분.
- 길이 정책: 영상 10분당 본문 800~1,200자 기준, 상한 6,000자. 60분 넘는 영상은 구간 수를 늘리고 요약 밀도를 낮춤.

정확도 장치

- 모든 문장에 타임스탬프 강제 → 렌더링 시 `[12:40]`을 해당 시점 영상 링크(`?t=760`)로 변환. 독자에게도 유용하고 환각 검출도 쉬움.
- 자동생성 자막의 고유명사 오류: 제목/설명/태그를 "정답 후보 사전"으로 함께 넣어 교정.
- Pass 4에서 근거 없는 문장이 20% 넘으면 재생성, 두 번 실패하면 `needs_review`로 사람에게.

### 2.4 비주얼 생성

세 계층으로 나눈다. **왼쪽일수록 안전하고 기본값.**

| 유형 | 생성 방법 | 저작권 | 용도 |
|---|---|---|---|
| A. 인포그래픽/카드 | HTML 템플릿 → Playwright 스크린샷 PNG | 우리 것 | 핵심 포인트 카드, 대표 이미지(OG), 구간 요약 카드 |
| B. 다이어그램/차트 | Mermaid → PNG, matplotlib | 우리 것 | 흐름·비교·구조, 영상에 나온 수치 |
| C. AI 일러스트 | 이미지 생성 모델 | 우리 것(정책 확인) | 대표 이미지 감성 보강 |
| D. 장면 캡처 | yt-dlp로 영상 받아 ffmpeg로 특정 시각 프레임 추출 | **타인 저작물** | 화면 공유·슬라이드·데모가 핵심인 영상만 |

캡처(D)를 쓸 때의 절차

1. Pass 2의 `visual_suggestion.type == "capture"` 인 구간만 대상.
2. 해당 구간에서 장면 전환 감지(ffmpeg scene filter)로 후보 3~5장 추출.
3. 후보를 비전 모델에 보내 "슬라이드/화면공유/제품 등 정보가 담긴 프레임인가, 아니면 말하는 얼굴·검은 화면인가"를 판별하고 1장 선택 + 캡션 생성.
4. 저해상도(가로 800px)·출처 표기·타임스탬프 링크와 함께 삽입. 채널별 `visual_policy`로 끌 수 있게.

여기에 **원 영상 임베드(iframe)**는 항상 넣는다. 공식 허용 방식이고 원작자에게 트래픽이 가서 분쟁 여지를 줄인다.

### 2.5 글 조립 & 발행

글 템플릿(순서 고정, 채널별 미세조정 가능)

```
대표 이미지(A/C)
한 줄 요약 + 이 글에서 얻는 것 3가지
영상 임베드
핵심 포인트 카드(A)
구간별 상세 (소제목 + 본문 + 인용 + 해당 시각 링크 + 필요 시 B/D 이미지)
용어집 / FAQ
부가가치 블록(배경 설명, 관련 자료)
출처·저작권 고지 (채널명, 원본 링크, 캡처 사용 시 인용 고지)
```

발행 대상 플랫폼 비교(한국 상황)

| 플랫폼 | 자동 발행 | 비고 |
|---|---|---|
| WordPress(자체호스팅/wp.com) | REST API 정식 지원, 이미지 업로드 API 있음 | **1순위**. 플러그인·SEO·애드센스 생태계 |
| 정적 사이트(Astro/Hugo + GitHub Pages/Firebase Hosting) | 마크다운 커밋 → 빌드 | 비용 0, 완전 자동화, 댓글·플러그인은 별도. **2순위** |
| Blogger | 공식 API | 가능하나 성장성 낮음 |
| 티스토리 | Open API 종료(2024) | 브라우저 자동화만 가능 → 비추천 |
| 네이버 블로그 | 공개 API 없음 | 브라우저 자동화는 약관 위반 리스크. "초안을 만들어 두고 사람이 붙여넣기"까지만 |

권장: **WordPress를 본진**으로 두고, 필요하면 네이버는 반자동(초안 복사)으로 병행.

### 2.6 승인 게이트 — 다빈보드 연동

이 저장소(다빈보드)에 이미 있는 것: Firebase Auth, Firestore, FCM 웹푸시, 모바일 PWA UI. 그대로 활용하면:

- 파이프라인이 `yt_posts/{video_id}` 에 초안(HTML, 이미지 URL, 상태)을 쓰면 → 기존 FCM 경로로 "새 초안 도착" 푸시
- 다빈보드에 "블로그" 탭 하나 추가: 초안 미리보기, 제목/문단 간단 수정, **승인 / 반려(사유) / 재생성** 버튼
- 승인되면 Cloud Function 또는 다음 스케줄 실행에서 WordPress로 발행, 상태 `published` 로 갱신
- 채널 등록/정지, 채널별 `publish_mode` 전환도 같은 탭에서

`publish_mode: auto` 채널은 게이트를 건너뛰되, Pass 4 검증 실패·이미지 생성 실패 시엔 강제로 `review`로 떨어지게.

### 2.7 데이터 모델 (Firestore)

```
yt_channels/{channel_id}        채널 설정 (2.1 참조)
yt_videos/{video_id}            { channel_id, title, published_at, duration, status,
                                  transcript_source: manual|auto|stt, attempts, last_error, cost_usd }
yt_posts/{video_id}             { summary_json, html, images: [{type, url, caption}],
                                  seo, review: {state, reviewer, note}, wp_post_id, published_url }
yt_runs/{run_id}                실행 로그 (시작/종료, 처리 건수, 실패, 총비용)
```

상태 전이: `discovered → fetched → summarized → illustrated → drafted → (review|approved) → published`, 실패 시 `failed:{stage}` 와 `attempts` 증가, 3회 초과면 `dead` + 푸시.

## 3. 기술 스택 제안

| 영역 | 선택 | 대안 |
|---|---|---|
| 언어 | Python 3.12 | TypeScript(Cloud Functions와 통일하고 싶다면) |
| 수집 | yt-dlp, youtube-transcript-api, ffmpeg | — |
| STT 폴백 | Whisper 계열 API | faster-whisper 자체 호스팅 |
| LLM | Anthropic SDK(`anthropic`), 구조화 출력, 프롬프트 캐싱, Batch API | — |
| 이미지 | Playwright(HTML→PNG), mermaid-cli, matplotlib, 이미지 생성 API | — |
| 상태/큐 | Firestore | SQLite(단일 서버라면) |
| 스케줄 | GitHub Actions cron(무료, 30분 주기) | Cloud Scheduler + Cloud Run Job |
| 발행 | WordPress REST API | Astro + GitHub Pages |
| 승인 UI | 다빈보드(index.html) 탭 추가 | 별도 관리 페이지 |
| 알림 | 기존 FCM | 카카오톡 나에게 보내기 |

참고: Anthropic **Managed Agents의 스케줄 배포**로 "매일 밤 채널을 훑고 글을 쓰는 에이전트"를 서버리스로 두는 방법도 있음. 다만 이 작업은 흐름이 고정된 파이프라인이라 코드가 루프를 쥐는 방식(Claude API + 도구 호출)이 디버깅·비용 통제에 유리. 에이전트형은 Phase 3 이후 "관련 자료 조사" 같은 개방형 단계에서 검토.

## 5. 품질 기준 (완료 정의)

## 부록 A. 요약 프롬프트 골격 (Pass 2, 구간별)

```
[시스템]
당신은 유튜브 영상 내용을 블로그 독자에게 정확하고 상세하게 전달하는 에디터입니다.
- 자막에 없는 내용은 절대 추가하지 않습니다. 추측이 필요하면 "영상에서 명시하지 않음"이라고 씁니다.
- 모든 항목에는 근거가 되는 자막 타임스탬프(mm:ss)를 붙입니다.
- 자막은 자동 생성일 수 있어 고유명사 오탈자가 있습니다. 제목/설명/태그에 있는 표기를 우선합니다.
- 결과는 지정된 JSON 스키마로만 출력합니다.

[유저]  (캐시 대상: 영상 메타 + 전체 자막)
<video> 제목/설명/태그/챕터 </video>
<transcript> [00:00] … </transcript>

(구간별 요청, 캐시 이후)
구간 {n}: {start}~{end}, 제목 "{title}" 을 위 스키마의 sections[] 한 개 항목으로 작성하세요.
detail 항목은 최소 4개, 인용은 1~3개, 수치가 나오면 numbers에 모두 기록하세요.
이 구간을 이미지 한 장으로 표현한다면 어떤 유형(diagram/chart/card/capture)이 가장 이해를 돕는지
visual_suggestion에 구체적으로 적으세요. capture는 화면공유·슬라이드·데모가 있을 때만 제안합니다.
```
